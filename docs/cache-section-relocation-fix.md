# 共享缓存数据节重排修复

## 问题与证据

2026-10-27，本机 Ryzen 7 5800H / PCI `1002:1638`、macOS 26.7.2
`25G332`，加载 `f8179e5` Release 的 NootedRed，UUID 为
`230232C2-0EFE-3832-BC92-869F943E0147`。
13:47–13:55 导出的 19 份 GPU 重置报告均指向 `mediaanalysisd` 的
`computeUQ3 / VTMTSComputeFunction`；另有一份较早的 Chrome GFX 报告。
这与用户报告的整个桌面和鼠标周期性停顿相符。

显示修复开关与 ComputeScratch 已注册，但没有 Applied 标记，存在动态匹配拒绝。
只读真实缓存复现：整组显示修复、独立 Scratch 和视频修复解析失败。
当前缓存 UUID 为 `21FB8708-FC8E-3765-BE8C-65D612CDF049`。

原解析器允许映像和已匹配函数搬迁，但仍以映像起点加固定 RVA 核对外部数据。
本次缓存独立移动了 `__DATA`、`__DATA_CONST` 中的多个节，导致相同的
Objective-C 引用和运行时全局数据被误判为错误目标。
此外，渲染管线构造函数按原始完整字节比较，57 个重定位字节变化使匹配失败。
完整反汇编核验发现构造函数及另外 21 个参考函数的差异均位于外部重定位字段，
未发现这些函数的其他指令字节改变。

## 实现

- 外部数据目标按映像路径、段名、节名和节内偏移核验，支持各数据节独立移动。
  Mach-O 命令位置仅作提示；提示不命中时按名称和边界重新定位。
- 构造函数核验全部非重定位字节、98 个外部引用及其直接／间接绑定关系，
  只改原有的混合能力分支，不通过忽略整段代码来接受未知实现。
- Scratch 和视频载荷重建直接数据引用，GOT／调用桩继续按真实绑定核验。
- Tahoe 的 SubmitGuard 改为完整提交方法核验与动态定位，不再因未知缓存 UUID
  自动关闭；保留已安装跳板的身份验证。
- 复用 Scratch 已建立的映像索引，避免同一事务重复扫描整个映像目录。
- 节范围检查使用 64 位长度，避免大尺寸截断。

没有新增系统小版本或 UUID 白名单。现有 14 / 15 路径和已验证缓存的静态路径保留。
代码段中的已匹配函数继续按完整函数身份搬迁；其他代码目标保留原有核验。
数据节内对象顺序、函数真实指令或 ABI 改变时，仍需新的语义证据；本修复不宣称
任意未来系统均可自动打补丁。

`tools/build_cache_section_targets.py` 从真实缓存生成目标节坐标与构造函数元数据。
生成前核验全部非重定位字节、指令边界、目标映像和每个数据节的一致位移；
真实指令变化或同一节内布局变化会拒绝生成。生成文件不手工编辑。
运行时不读取驱动文件，也不修改磁盘上的共享缓存。

## 验证与安装验收

初版只读真实缓存检查：六种核显显示计划均成功，读取次数 27,641；四种 VCN 视频
计划均成功，读取次数 15,075；完整提交方法解析成功。
这些结果均在现有的 32,768 次读取与 32 MiB 读取预算内。

新增 CPU 回归覆盖独立数据节重排、完整构造函数搬迁、未知 UUID、每个重定位
目标破坏、非重定位指令变化、元数据／读取失败和 64 位边界。
现有跨页事务回滚、Sequoia 及旧系统回归继续检查。
完整结果、三配置构建和静态分析状态以交付包中的验证记录为准。

构建使用 `f8179e5` 的干净归档与本次修改，不包含工作区已有的 EC／背光改动。
参数继续使用 `-NRedDisplayFix -NRedVideoFix NRedECFix=1`，无需恢复旧参数。

安装后检查：

```sh
ioreg -lw0 -r -n IGPU | rg 'NRed(CacheSectionRevision|ComputeScratchApplied|LegacyBlendWindowServerApplied|SubmitGuardWindowServerApplied|VCNUserApplied)'
```

预期 `NRedCacheSectionRevision=1`，并在相应新进程启动后出现各 Applied 标记。
这些标记只证明代码写入与页面保护恢复，不能代替 GPU 执行成功。
继续观察原有媒体分析负载、桌面／鼠标响应和 GPU 完成情况，并对照统一日志和
新 `.gpuRestart`；没有新增报告文件本身不能证明挂起消失。

本轮不自动替换 EFI、不修改 CoreMedia 偏好、不暂停后台服务或重启系统。
硬件卡顿是否消失仍需安装新包并重启后验收。

## 动态解析的 CPU 与栈开销

在 `cadb94c` 的第一阶段安全守卫基础上继续优化本修复的公共解析路径：

- 同一事务中，已完整读取并检查重复路径的映像目录可供后续路径子集复用。
  SubmitGuard 与显示解析共用 Input 和读取预算；视频设备适配与安全守卫也复用目录。
  每次仍重新核验 Mach-O、完整函数、相对引用、绑定和候选唯一性。
- 前缀比较使用四个 64 位掩码字；原生与已补丁前缀相同时只比较一次。
  其含义与原逐字节谓词相同，未扩大重定位掩码。
- 显示与视频事务在各自的堆工作区提供 4 KiB 扫描缓冲；渲染解析的 Input、Image
  和构造函数映像边界表也放在堆工作区。无缓冲调用仍使用独立的 1 KiB 栈缓冲路径。
  扫描回调按引用传递，避免 Debug 中逐层复制闭包。

这些数据只活到本次事务结束，不跨进程保存命中或拒绝结果，不以 UUID、PID
或上一次匹配结果代替当前核验。动态匹配发生在共享缓存检查钩子中，未向逐帧渲染
或编解码路径添加解析工作。

本机 `21FB8708-FC8E-3765-BE8C-65D612CDF049` 缓存只读对照：分别编译
`cadb94c` 与修改后的真实解析器，以相同 `clang++ -O2`、原生文件读取器顺序运行
五轮，显示覆盖六种设备数据，视频覆盖四种。下表 CPU 时间为进程 CPU 中位数，
包含文件读取和解析开销，不是内核钩子的实测时间或系统总 CPU 占用率。

| 项目 | 优化前 | 优化后 |
|---|---:|---:|
| 独立显示解析：预算内读取次数 | 27,641 | 10,660 |
| 独立显示解析：CPU 时间 | 51.584 ms | 29.440 ms |
| 视频与安全守卫：预算内读取次数 | 28,079 | 8,438 |
| 视频与安全守卫：CPU 时间 | 53.335 ms | 21.806 ms |
| 显示与 SubmitGuard：底层读取调用数 | 35,168（两次独立解析之和） | 11,674（共用事务） |

单独调用兼容的无缓冲 SubmitGuard 接口仍约 7,512 次底层读取；生产桥接已使用
共用堆缓冲接口。底层调用数还包含缓存头与回读，不等同于 Input 的预算计数。
共用显示事务读取约 21.6 MB，仍受 32,768 次／32 MiB 的共同上限约束。

按实际 kext 编译选项复测，含外层钩子的可见内部调用链上界如下：

| 配置 | 优化前 | 优化后 | 最大单帧（优化后） |
|---|---:|---:|---:|
| Debug | 6,768 B | 6,288 B | 1,816 B |
| Research Release / Release | 5,088 B | 4,184 B | 1,576 B |

均低于调用链 8 KiB、单帧 2 KiB 预算。这个保守上界也包含未使用堆缓冲的回退分支，
但不包含内核 VM、IOKit、copyin/copyout 和锁的实现栈。

新增 33,892 项 ASan/UBSan 扫描检查，覆盖掩码等价、非对齐与缓冲边界、重复候选、
完整函数损坏、读取与预算失败以及索引生命周期。另通过节重排 137 项、动态显示
63 项、Tahoe Scratch 95 项、Sequoia 显示 124 项、两个系统各 45 组 VCN 事务故障注入、
旧系统桥接、三配置构建和静态分析。真实缓存检查未创建 GPU 设备或提交 GPU 命令。
这些结果证明解析开销降低；安装后系统持续 CPU 占用和显示、编解码行为仍待实测。
